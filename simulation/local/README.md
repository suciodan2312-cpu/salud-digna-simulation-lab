# Laboratorio local de la fase 3

`corepack pnpm start lab-plan` muestra el plan sin tocar servicios. La copia de ejecución se extrae del commit `ff989cc` a una carpeta privada bajo `reports/`. PostgreSQL usa un clúster nuevo con SCRAM en `127.0.0.1:55432`. Las dos bases nuevas llevan la marca `salud-digna:synthetic-only`. La API escucha en `127.0.0.1:13100` y el orquestador en `127.0.0.1:13300`. WhatsApp externo y OpenAI quedan desactivados. La conversación interna de desarrollo es opcional para validar su contrato.

## Secuencia autorizada

1. Con autorización para clúster, migraciones y servicios, ejecutar desde la raíz del worktree `powershell -NoProfile -ExecutionPolicy RemoteSigned -File .\simulation\local\prepare.ps1 -ApproveNewLocalLab`. La política se aplica solo al proceso hijo. `-AllowRegistry` permite consultar el registro oficial para completar la verificación del lockfile. Si falla antes de iniciar el clúster, conservar el intento y usar otro valor de `-Attempt`; si pudo iniciar, reconciliar los puertos antes de repetir. Los archivos `simulation.env` y los logs privados se quedan fuera de Git.
2. Desde `simulation/`, ejecutar `dataset-validate 3ec1448fee9783a2150ccefc` y `copy-plan 3ec1448fee9783a2150ccefc`. Con el entorno privado cargado y `SIM_COPY_CONFIRM=salud-digna:synthetic-only`, usar `copy-preflight <id>` para verificar marcas, migraciones y tablas vacías en una transacción de solo lectura. Ejecutar `copy-load <id>` solo tras la aprobación específica de COPY. A continuación, `copy-audit <id>` verifica conteos por tabla, journal y consistencia del flujo antes de aprovisionar actores. La auditoría espera exclusivamente filas del corpus.
3. Tras la autorización de aprovisionamiento, un paciente usa `profile nuevo` con semilla elegida y contraseña ficticia privada. El correo queda en `example.test`. En una terminal interactiva y desde la copia privada de `apps/api`, utilizar `node dist/auth/create-advisor.js` y `node dist/auth/create-admin.js`. El programa oficial lee contraseñas sin mostrarlas. Los tres canales requieren registros previos. El helper `dist/local/channels.js` crea esas filas de fixture y usa la CLI oficial para emitir las credenciales con los scopes adecuados. Requiere `SIM_CHANNEL_PROVISION=local-fixtures` y protección COPY local. Recibe como argumento la ruta relativa `reports/local-lab-ff989cc[-N]`. `channels.env` es privado y se carga junto a `simulation.env`. Los recorridos usan solo JWT y grants emitidos por los servicios.
4. Comprobar individualmente `basic`, `schedule`, `assisted`, `admin`, `appointment-status`, `version-conflict`, `idempotency`, `continuity` y los perfiles con los actores correspondientes. Abrir una solicitud con un perfil de prueba antes de comprobar reanudación. El catálogo debe tener dos estudios activos para el perfil indeciso. Los recorridos del orquestador son independientes del agendamiento central.
5. Con los recorridos comprobados, obtener el JWT de paciente fuera de k6 con `dist/local/token.js` y el directorio del laboratorio. Requiere `SIM_ALLOW_WRITES=true` para login y guarda el JWT en `smoke-token.env`. Autorizar por separado el smoke real. Establecer `SIM_LOAD_SCENARIO=smoke`, `SIM_SMOKE_PATIENT=true`, los puertos del laboratorio y `SIM_K6_CONFIRM=isolated-loopback`. El plan usa un VU y una iteración, solo lecturas, y exporta JSON/CSV. Activar el dashboard HTML en el proceso de k6 si se desea. La segunda configuración es `habitual` con tasa máxima de 5/s, hasta 5 VUs y duración corta, para revisión posterior.

Los parámetros privados pueden suministrarse con `node --env-file=<archivo> dist/cli.js <comando>`. Evita pasar secretos como argumentos de terminal y mantener salidas crudas de APIs. Las cuentas del corpus histórico no sirven para autenticar.

## Ser­vidor desplegado

`SIM_PATIENT_PORTAL_URL`, `SIM_CALL_CENTER_URL` y `SIM_ADMIN_URL` describen interfaces web. La API y el orquestador tienen variables propias. Las interfaces sirven solo como metadatos de planificación. Para comparar contratos, pide al equipo un OpenAPI de la API central y la revisión del orquestador exportados por su proceso autorizado. Ejecuta `compare-contracts <archivo-local.json>` y revisa las secciones divergentes. Contrasta rutas, DTO, scopes, permisos, HMAC, expiraciones, rate limits y banderas con las fuentes auditadas. Una coincidencia del OpenAPI no acredita el estado del despliegue ni la compatibilidad de las capacidades del orquestador.

La autorización futura debe identificar el entorno de pruebas, los orígenes HTTPS, certificados válidos, prefijos, límites aprobados y propietarios. Ambos transportes conservan el bloqueo remoto.
